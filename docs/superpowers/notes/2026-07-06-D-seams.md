## 1a. Trained-member task-creation chokepoint

**Verdict: a small, well-defined set of server-side functions — not one — all funnelling
into two generated inserts (`CreateAgentTask`, `CreateChatTask`).** `agent_id` and the
owning `project_id` are resolvable at each.

Channel/DM path (leader @mentions a member in a channel):

  `enqueueChannelAgentPrompt` (calls at `:1859`/`:1861`/`:1863`)

Sub-issue "child done" fan-in:

  `:344` `EnqueueTaskForSquadLeader` (squad parent).

All of the above resolve to the shared `TaskService` funcs in

- `:544` `EnqueueTaskForMention` / `:554` `EnqueueTaskForSquadLeader` →
  `enqueueMentionTask` → **`:573`
  `s.Queries.CreateAgentTask(ctx, db.CreateAgentTaskParams{ AgentID: agentID, IssueID: issue.ID, ... })`**
- `:756` `EnqueueChatTask` (+ Fresh/Ambient) → `:774` `enqueueChatTask` → **`:787`

At each, `agent_id` is explicit and the project is one hop away: the `issue` carries

### (ii) POST /api/agent/start with parent_task_id — **NOT in this server**

There is **no `/api/agent/start` route** in the multica Go router
(`cmd/server/router.go`; only `/api/agents*`, `/api/agent-tasks`,
`/api/daemon/tasks/{taskId}/start` = `h.StartTask`, which is a dispatched→running
*transition*, not creation). The db_bridge channel `agent_start`
(`POST /api/agent/start`, `multica/db_bridge/channels.py`) is in the `leagent_api` group
and targets "the le-agent API" (a different SaaS service), not this Go server.

`agent_task_queue.parent_task_id` exists but is only written by the auto-retry
(`service/task.go` `CreateRetryTask` in `MaybeRetryFailedTask`, ~`:1660`) and autopilot
copy paths — not by a leader/runtime "spawn subordinate" API in this repo. **A runtime
does not call back to create teammate tasks; leader delegation happens entirely through
the @mention/comment path (i).**

### env_dispatch's own creation site (leader / single-agent-at-dispatch)

The dispatch's *leader* task (and a single-agent dispatch's task) is created by a
**different** path that bypasses `TaskService.Enqueue*`:
`internal/handler/env_dispatch.go:607` `(*envDispatchDepsAdapter).EnqueueAgentRun` →
`:642` `CreateAgentTask` (issue) / `:697` `CreateChatTask` (chat). If
`train_agent_id == agent_id` (single-agent training, allowed by spec §4.1), the trained
task is created HERE at dispatch, not via a later mention. **The open-hook must
therefore cover both families** (the `Enqueue*` set AND `EnqueueAgentRun`), or hook the
lowest common denominator (`CreateAgentTask`/`CreateChatTask`). Both have `agent_id` +
project resolvable.

## 1b. Completion path (session-close hook attach point)

Server-side terminal transitions live in `internal/service/task.go` and are invoked from
the daemon report handlers:

- **complete**: `service/task.go:1285`
  `CompleteTask(ctx, taskID, result, sessionID, workDir)` → `qtx.CompleteAgentTask`.
  Called from `handler/daemon.go:2086` `CompleteTask` (route
  `router.go:528 POST /api/daemon/tasks/{taskId}/complete`).
- **fail**: `service/task.go:1468`
  `FailTask(ctx, taskID, errMsg, sessionID, workDir, failureReason)` →
  `qtx.FailAgentTask`. Called from `handler/daemon.go:2237` `FailTask`
  (`router.go:529 .../fail`).
- **cancel**: `service/task.go:905` `CancelTask` / `:915` `CancelTaskWithResult`; daemon
  `handler/daemon.go:2444 CancelTask`; user `handler/chat.go:935 CancelTaskByUser`
  (`router.go` `POST /api/tasks/{taskId}/cancel`). Bulk cancels: `:819`
  `CancelTasksForIssue`, `:838` `CancelTasksForAgent`, `:860`
  `CancelTasksByTriggerComment`.

`CompleteTask`/`FailTask` return the finalized `*db.AgentTaskQueue`, which carries
everything the close hook needs: `pkg/db/generated/models.go:114` `type AgentTaskQueue`
→ `:126 Context []byte`, `:128 SessionID pgtype.Text`, `:131 ChatSessionID pgtype.UUID`,
plus `IssueID`. So `task.context` (→ `areal_proxy`), the stored `session_id`, and the
owning project (via `IssueID`→project or `ChatSessionID`→project) are all available.

**Caveat (timeout / stale) — bypasses `TaskService`:** the sweeper
`cmd/server/runtime_sweeper.go:247` transitions stuck `dispatched`/`running` and expired
`queued` tasks to failed via **`queries.FailStaleTasks(...)` SQL directly** — it does
NOT call `TaskService.FailTask`. A training task that times out this way will **not**
hit a close hook placed in `FailTask`. Spec §4.5 already scopes a stale-session reaper
out of D, so this is consistent, but it means "failed via timeout" is not covered by the
D7 close hook (see deviations).

## 1c. execenv provider override — **NEEDS-NEW-FIELD**

**There is no existing per-task, `context`-sourced provider/base_url/api_key override.**
Everything is per-*agent* or per-*runtime*:

- Provider is **per-runtime** (`daemon.go` runner `run(ctx, task, provider, ...)`;
  `provider` from the runtime index `d.runtimeIndex`), not from `task.context`.
- Model: `daemon.go:~3000` two-tier `task.Agent.Model` → `entry.Model`
  (`MULTICA_<PROVIDER>_MODEL`); no context override.
- Env (api key / base url): `daemon.go:2965 Env: agentEnv`, built from base env
  - `task.Agent.CustomEnv` (`daemon.go:~2952` loop, blocklist-guarded). This is where an
    agent's `ANTHROPIC_BASE_URL`/`ANTHROPIC_API_KEY` router config lives — but it is
    **agent-scoped**, not task-scoped.
- ExecOptions assembled at `daemon.go:3039` (`Model: model` `:3041`,
  `CustomArgs: customArgs`). `pkg/agent/pi.go` `buildPiArgs` derives
  `--provider`/`--model` from `opts.Model` ("provider/model"); api key / base url flow
  only via `cmd.Env = buildEnv(b.cfg.Env)` (pi.go). `pi` does **not** emit `--api-key`
  (spec §1's `--api-key` would have to be a custom arg or env).

The claim-response `Task` struct (`internal/daemon/types.go`) has **no generic `context`
field and no provider/base_url/api_key field** — only specific extracted fields
(`SquadID`, `AutopilotRunID`, …). `AgentData` (`types.go:~131`) carries `CustomEnv`,
`CustomArgs`, `Model`. The claim builder `handler/daemon.go:1066 ClaimTaskByRuntime`
assembles `TaskAgentData` (`:~1116`) from `agent.CustomEnv`/`CustomArgs`/`Model`.

**Verdict: NEEDS-NEW-FIELD** for a clean, provider-explicit path — either: (a) add an
`areal_proxy`/provider-override field to the daemon `Task` struct + populate it in
`ClaimTaskByRuntime` from `task.Context`, and consume it at the `daemon.go:3039`
ExecOptions site; **or** (b) **MINIMAL variant, server-only:** in `ClaimTaskByRuntime`,
when `task.Context.areal_proxy` is set, override the per-task `TaskAgentData.Model` (=
`"areal/areal-default"`) and `TaskAgentData.CustomEnv` (base_url/api_key env) — since
`TaskAgentData` is built fresh per claim. This needs **no daemon-side code change** IF
the trained agent's runtime provider is `pi` (which maps `Model`→`--provider`/`--model`
and reads key/url from env). Risk: `provider` is runtime-scoped, so the trained runtime
must already be a `pi` runtime, and the exact env-var names `pi` honours for
base_url/api_key must be confirmed.

Exact structs/functions to touch: `internal/daemon/types.go` `Task` + `AgentData`;
`internal/handler/daemon.go` `ClaimTaskByRuntime` (`:1066`) / `taskToResponse`
(`handler/agent.go:305`); `internal/daemon/daemon.go` ExecOptions build
(`:2965`/`:3039`); provider flag build `pkg/agent/pi.go` `buildPiArgs`.

## 1d. start_session task_id semantics + set_reward/end_session shapes

`areal/v2/inference_service/data_proxy/session.py`:

- `StartSessionRequest{ task_id: str; api_key: str|None; group_size: int=1 }`
- `SessionStore.start_session` builds `session_id = f"{task_id}-{idx}"` (idx
  disambiguates collisions). **`task_id` is only a namespacing prefix for `session_id`;
  it is not otherwise interpreted.**
- `StartSessionResponse{ group_id: str; sessions: list[SessionCredentials] }`,
  `SessionCredentials{ session_id, session_api_key }`.
- `SetRewardRequest{ interaction_id: str|None; reward: float; model: str|None }` — **no
  `session_id`** in the body; the session is resolved from the caller's bearer token.

**What multica should pass as `task_id`:** the multica **`agent_task_queue.id`** (the
trained task's UUID string). Each trained task = exactly one session (`group_size=1`),
and the task id is the stable key multica already stores the returned `session_id`
against (spec §4.3). (`agent_run_id` is an env_dispatch response artifact that, in this
repo, *equals* the task id anyway — see `EnqueueAgentRun` returning `task.ID`.)

**Auth + which gateway actually serves `/rl/*` (important):** there are TWO
implementations and they disagree on shape/auth:

- `areal/v2/inference_service/gateway/app.py`: `POST /rl/start_session` (admin-key only,
  returns **201** `{group_id, sessions:[...]}`), `POST /rl/set_reward` (session-or-admin
  key). **No `/rl/end_session` route exists here.**
- `areal/experimental/openai/proxy/proxy_gateway.py:352` + backing
  `areal/experimental/openai/proxy/proxy_rollout_server.py`: implements all three.
  - `start_session` (`proxy_rollout_server.py:~440`, admin key) returns **flat
    `{session_id, api_key}` at 200** (NOT `{group_id, sessions}`).
  - `end_session` (`proxy_rollout_server.py:507`) — **session-key auth**
    (`session_id = Depends(_require_session_key)`); body is empty. Returns
    `{message, interaction_count}`.
  - `set_reward` (`proxy_rollout_server.py:~530`) — **session-key auth**; body
    `SetRewardRequest`.

Because D5's close hook needs `end_session`, and only the experimental stack serves it,
the executor behind the bridge is most likely the **experimental openai proxy gateway**.
Under that stack:

- `set_reward`/`end_session` are authenticated by the **session's `session_api_key` (=
  the `proxy_key`)**, not by a `session_id` argument and not by the admin key. So
  multica's close hook should call `set_reward`/`end_session` with the stored per-task
  proxy_key as bearer, passing only `{reward}` / empty body — NOT
  `set_reward(session_id, reward)`.
- `start_session` returns flat `{session_id, api_key}` (not `{group_id, sessions}`).

This diverges from spec §4.8 / plan Task 4, which assume the v2
`{group_id, sessions:[{session_id, session_api_key}]}` shape and an
`end_session(session_id)` signature (see deviations).

## Gateway/bridge confirm

`multica/db_bridge/channels.py` `CHANNELS` includes the **gateway group** (stub on the
leagent side, executor forwards to the AReaL host): `rl_start_session`
(`POST /rl/start_session`), `rl_set_reward` (`POST /rl/set_reward`), `rl_end_session`

`env_dispatch` (`POST /api/v1/env-dispatch`) — AReaL→leagent.

`chat_completions` in the same gateway group is the LLM traffic lane the trained runtime
uses (`base_url = http://db_bridge_stub:9100/v1` per spec §1/§4.7).

## Deviations from spec assumptions (affecting Tasks 2–8)

1. **No `/api/agent/start` in this server (1a-ii).** Delegation (ii) is not a code path
   here; teammate creation is exclusively the @mention/comment path. → Task 5 should
   target the `TaskService.Enqueue*` set (issue + chat) and the `EnqueueAgentRun`
   adapter; drop the "leader/runtime spawns subordinate via /api/agent/start"
   assumption.

1. **Two creation families, not one function (1a).** The open-hook must fire in both
   `service/task.go` `Enqueue*` (teammate) and `handler/env_dispatch.go`
   `EnqueueAgentRun` (leader / single-agent-at-dispatch). Cleanest: a shared helper
   invoked right after `CreateAgentTask`/`CreateChatTask` in each, or a thin wrapper
   query. Task 5 scoping should reflect this.

1. **1c is NEEDS-NEW-FIELD, not the "minimal existing field" the spec hoped for.** Task
   6 must add plumbing (either a new daemon `Task`/`AgentData` field, or a claim-time
   override of per-task `AgentData.Model`+`CustomEnv`). The MINIMAL server-only variant
   is viable but depends on the trained runtime being `pi` and on `pi`'s env-var
   contract for base_url/api_key — confirm before committing to it.

1. **RL contract shape/auth mismatch (1d) — highest-impact.** The `end_session`-capable
   gateway (experimental openai proxy) uses **flat `{session_id, api_key}`** and
   **session-key auth** for `set_reward`/`end_session` (no `session_id` in body),
   whereas spec §4.8 / plan Task 4 assume the v2
   `{group_id, sessions:[{session_id, session_api_key}]}` shape and an
   `end_session(session_id)` signature. → Task 4 (Go RL client) must (a) confirm which
   gateway AReaL runs behind the stub, and (b) most likely: parse a flat
   `{session_id, api_key}` from start_session, store `proxy_key=api_key`, and call
   `set_reward`/`end_session` **authenticated with the per-session proxy_key** (admin
   key only for start_session), sending `{reward}` / empty body rather than a
   `session_id` argument.

1. **Timeout/stale close-hook gap (1b).** The sweeper (`FailStaleTasks`, raw SQL)
   bypasses `TaskService.FailTask`, so a training task that times out won't emit the
   default reward + `end_session`. Consistent with spec §4.5 (reaper is out of scope for
   D) but should be called out as a known non-coverage in Task 7.

1. **`task_id` = multica `agent_task_queue.id` (1d).** Confirmed as the right value to
   pass to `start_session`; `session_id` is derived as `"{task_id}-{idx}"`. No change
   needed, just pinned.
